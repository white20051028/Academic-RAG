# v15 · RAG 失败就进 Agent 兜底

> 2026-11-13 设计。**本文只讲设计，不写代码。**
>
> 目标：让 P2 在「分情况讨论」的难题上不再拒答，同时把判断层从「拦截器」改成「路由器」。
> 这不是「加一个 Agent 功能」，是**把一个 RAG 升级成「RAG + Agent 兜底」的分层架构**。

---

## 一、为什么做：一个真实失败案例

用户实测（反馈第 7 条）：

```
问：大三绩点 4.0 能转专业吗
答：能。依据：绩点不低于 3.00。
```

**正确答案是不能。** 2026 版转专业通知里：

```
第二条（一）（二）绩点3.00 / 排名前30%   → 第四条（一）限定本科一年级
第二条（八）（九）兴趣专长 / 学习困难      → 第四条（二）限定本科一至三年级
```

「绩点 4.0」这条在大三**根本不适用**。

### 根因不是检索，是「资料的结构」

资料里「绩点 3.00」和「限定本科一年级」在同一份文件里，但在**不同的 chunk**：

```
chunk A：第二条（一）…平均学分绩点不低于3.00 且满足拟转入专业接收条件的…
chunk B：第四条（一）符合第二条第一～二款规定需申请转专业的学生限定本科一年级…
```

检索把两个都召回了（实测 top-10 里 4 条带年级限制），**但模型看到的是碎片，不知道它们的关系**。

### 一句话总结

> **RAG 能拿到「相关片段」，但拿不到「片段之间的关系」。**
> 而「转专业」这种分情况讨论的规定，答案恰恰在关系里。

这就是 Agent 要解决的问题——**让它自己发现「不够」，自己再查一次**。

## 二、改完长什么样

### 场景 A：普通问题（80%，速度不变）

```
问：转专业要什么条件
→ 判断层：②够用
→ RAG 直接生成
→ 耗时 6 秒，成本 0.0065 元       ← 和现在完全一样
```

### 场景 B：分情况的难题（会走 Agent）

```
问：大三绩点4.0能转专业吗

步骤 1  检索 → 判断层：③不够（资料只说限定一年级，没说大三怎么办）
        ↓
步骤 2  read_full("2026转专业通知") → 看到完整条款
        ↓
步骤 3  判断层（第二轮）：②够用了
        ↓
        生成：「你不能走绩点那条（只限大一），
              但可以走第八、九款（兴趣专长/学习困难），限定一至三年级」
```

**耗时约 15 秒，成本约 0.02 元。** 慢 2.5 倍、贵 3 倍，但**答对了**。

### 场景 C：Agent 也查不到

```
步1 search → 步2 read_full → 步3 再查一次
→ 判断层仍然：③不够
→ 退回现在的拒答 + 指路（不硬答）
```

### 场景 D：闲聊（判断层顺手解决）

```
问：吃什么
→ 判断层：①无关
→ 彩蛋话术，不检索、不进 Agent
```

## 三、架构变化：判断层从「拦截器」变成「路由器」

### 现在

```
检索 → 判断层（够/不够） → 够：生成 ｜ 不够：拒答
                              ↑
                        这里是个死胡同
```

### 改后

```
检索 → 判断层（三分类）
         ├─ ① 闲聊/无关  → 话术回复（不生成）
         ├─ ② 够用       → 生成（快路径，80%）
         └─ ③ 不够       → Agent 循环（兜底，20%）
                              ├─ read_full 读完整文件
                              ├─ 再判断
                              └─ 3 步后仍不够 → 拒答 + 指路
```

**关键点**：判断层不再「拦住」，而是「分流」。

---

## 四、判断层三分类设计

### 输出格式

```
A | 原因：<为什么无关>
B | 依据：<摘出资料里能用的那句话>
C | 原因：<缺什么，或者需要分情况讨论>
```

用 A/B/C 而不是「够/不够/无关」——**单字母不会像「能不能」那样产生歧义**（v14 踩过「能」的两个意思）。

### 最容易判错的是 B 和 C，给模型一个自问的方法

```
问自己：用户看完这些资料，还需要自己去翻文件吗？
  需要 → C
  不需要 → B
```

**C 的典型特征**：「问题需要分情况讨论，资料只覆盖了其中一种情况」。

例子：

| 问题 | 资料 | 分类 |
|---|---|---|
| 转专业要什么条件 | 全部条款 | B |
| 大三能转专业吗 | 只说「限定一年级」 | **C**（大三怎么办没说） |
| 挂科了怎么办 | 补考、重修都有 | B |
| 我这种情况能转吗 | 没有具体情形 | **C** |

### 三分类顺手干掉了一个老 bug

现在的 `refusal_kind()` 是**关键词表**判断「是不是无关」：

```python
ACADEMIC_WORDS = ("学籍", "学分", "转专业", ...)
# 没有「兵役」「上课」
```

结果「我想大学期间服兵役」被秒拒（资料里明明有答案，11-13 修过一次）。

**换成 DeepSeek 三分类，这张词表可以删掉。** 关键词判断永远补不全，语义判断不会。

## 五、两个工具

### `search(query) -> list[片段]`

- 就是现在的 `search_mod.search()`
- 返回 top-5 片段 + 来源文件名
- **不变**

### `read_full(doc_name) -> str`

- 读 `data/processed/` 下**一份完整文件**
- 为什么需要：chunk 是切开的，「限定一年级」和「绩点3.00」不在一起
- 一次返回全文（约 3000–8000 字）

**代价**：4000 tokens ≈ 0.004 元/次。这是 Agent 贵的主要原因。

### 为什么不做另外两个

| 工具 | 不做理由 |
|---|---|
| `ask_user` | 会让体验**倒退**——现在是「一次列完规则 + 引导」，改成「停下来问你三轮」，用户要多等。而且 Streamlit 里实现「暂停等用户」很别扭 |
| `calc` | **收益为零**。模型算「155+15」「3.0-2.8」从来不会错；真正难的「按培养方案算该修多少学分」是检索问题，不是算术问题 |

## 六、Agent 循环

```
最多 3 步
每步：
  1. 判断层（三分类）
  2. 若是 C：
     - 第 1 次 C → read_full(最相关的那份文件)
     - 第 2 次 C → search(换一组查询词，用大模型重写)
     - 第 3 次 C → 放弃，退回拒答
```

**为什么第 1 步优先 `read_full` 而不是再 `search`**：

```
再 search 一次 → 拿到的还是碎片（同样的 chunk 库）
read_full 一次 → 看到完整条款，关系就出来了
```

**这是整个设计的核心判断**：问题不是「没查到」，是「查到了但拼不起来」。

### 步数上限为什么是 3

```
1 步：等于现在的 RAG
3 步：够覆盖「查一次 → 读全文 → 再补一次」的典型路径
5 步以上：成本线性涨，收益递减，而且模型容易在第 4 步开始乱调
```

## 八、验收标准

### 必须通过（否则不许上线）

| # | 测试 | 期望 |
|---|---|---|
| 1 | `大三绩点4.0能转专业吗` | 说出「绩点那条只限大一」+「第三年可走八九款」 |
| 2 | `转专业要什么条件` | 走 RAG 快路径，耗时 < 10 秒 |
| 3 | `吃什么` | 走 A 类，彩蛋秒回 |
| 4 | `我想大学期间服兵役` | 答「保留学籍至退役后2年」（不能因词表误判被拒） |
| 5 | `食堂几点开门` | 拒答 + 指路（Agent 也查不到，要能正确放弃） |
| 6 | 端到端 57 条评测 | 答对率 **不低于 78.9%**（不能因为改架构而变差） |

### 性能指标

| 指标 | 现在 | 目标 |
|---|---|---|
| 快路径耗时 | 6.5 秒 | **不变** |
| Agent 路径耗时 | — | < 20 秒 |
| 单次成本 | 0.0065 元 | 快路径不变；Agent 路径 < 0.025 元 |
| 内存 | 199 MB | < 300 MB（云服务器 1G 要撑住） |

### 回退方案

**侧栏那个「强制 Agent 模式」勾选反过来用**：默认关闭时，如果 Agent 路径连续失败 3 次，自动降级回纯 RAG。

**最坏情况**：删掉 `tools/agent.py` + 还原判断层，代码回到 `v1.3`。**所以要先打 tag。**

## 九、风险（诚实列）

| 风险 | 概率 | 应对 |
|---|---|---|
| **模型不按 A/B/C 输出** | 中 | 兜底：解析不到就按「B 够用」处理（保守，不阻断） |
| **C 类判太多，什么都走 Agent** | 中 | 先跑 57 条评测看 C 的比例，> 40% 就说明判据太松 |
| **read_full 撑爆上下文** | 低 | 单文件最长约 8000 字，DeepSeek 上下文 64K，够 |
| **端到端准确率变差** | 中 | 这是最大风险。**改之前先记下 78.9% 这个基线** |
| **1G 内存撑不住** | 中 | Agent 循环会增加内存（历史累积），要看 `free -h` |

## 十、这件事能怎么讲（面试用）

```
「我最初做的是标准 RAG：检索 → 生成。上线后收到一个反馈——
 学生问『大三绩点4.0能不能转专业』，系统答『能』，但正确答案是不能。

 我查下来，检索没问题，资料也召回了，问题是——

 资料里『绩点3.00』和『限定本科一年级』在同一个文件的不同位置，
 模型只看到碎片，不知道它们的关系。

 所以我把架构改成了分层的：
 80% 的问题一次检索就够，走快路径；
 判断层如果说『资料不够』，就自动进 Agent 循环，
 让它自己决定再读一次完整文件。

 关键设计是：Agent 第一步不是再搜一次，而是读完整文件——
 因为问题不是『没查到』，是『查到了但拼不起来』。
 再搜一次拿到的还是碎片。」
```

**这段话里有：发现问题的能力、定位根因的能力、架构决策、以及一个反直觉的判断（不重搜、读全文）。**

| | 新建 P3 | 升级 P2 |
|---|---|---|
| 数据 | 重抓 146 份 | 现成 |
| 评测 | 重做 57 条 | 现成 |

| 时间 | 2 周 | 2–3 天 |
| 讲法 | 「我还做了个 Agent」 | 「**我把一个 RAG 升级成了 Agent**」 |

**后者更能体现成长**——面试官想看的不是「你会几个技术」，是「你发现问题后怎么改」。

# v14：修好了检索污染，瓶颈转移到了判断层

> 这一轮修的是 v13 查出的第一个问题：**用户提供的个人信息会污染检索**。
> 修好了——但端到端分数没涨，因为瓶颈换地方了。

## 一、问题回顾

```
「我大二，绩点2.8，能转专业吗」→ 召回不到「平均学分绩点不低于 3.00」那条
「转专业 绩点要求」          → 能召回
```

「大二」「2.8」抢走了「转专业」的语义权重。

## 二、修法：不调措辞，改成多查几遍

先排除了一个错误方向：**调措辞**。

| 查询 | 能召回「3.00」吗 |
|---|---|
| 转专业 绩点要求 | ✅ |
| 转专业 绩点 要求 | ✅ |
| 转专业 绩点 | ❌ |
| 转专业申请条件 | ❌ |
| 转专业 要求 条件 流程 | ❌ |

同一个意图，差一个词就翻。**这是碰运气，不是工程。**

真正的修法：**多查几遍，合并结果**。

```
原话：我大二，绩点2.8，能转专业吗
 + 转专业 年级 要求      ← 每个槽位单独一个查询
 + 转专业 绩点 要求      ← 这条命中
 + 转专业 要求
 + 转专业 条件
→ 轮流合并，取 10 条
```

**关键细节**：不能把槽位拼在一起。

```
转专业 年级 绩点 要求   → ❌（「年级」稀释了「绩点」）
转专业 绩点 要求       → ✅
```

所以是「一个槽位一个查询」，不是「所有信息拼成一个」。

## 三、并发：串行 3.7 秒 → 0.76 秒

多查 4 遍，串行实测 3.7 秒。

但这 4 个查询彼此独立，等待可以重叠：

```python
with ThreadPoolExecutor(max_workers=min(len(queries), 5)) as pool:
    results = list(pool.map(one, queries))
```

**3.7 秒 → 0.76 秒，结果完全一样。**

上限 5 是因为再多人家的 API 会限流，收益也到顶。

## 四、单条验证：成功

```
我大二，绩点2.8，能转专业吗
  相似度 0.673 → 0.762
  rank 3 就是含「绩点不低于 3.00」那条
```

## 五、端到端：反而少 1 条

| | 之前 | 现在 |
|---|---|---|
| 真答对 | 33 | **32** |
| 答非所问 | 4 | **3** |
| 正确拒答 | 11 | 11 |
| 总正确 | 44/57 = 77.2% | **43/57 = 75.4%** |

**检索确实变好了**——评测里大量条目的相似度从 0.6x 升到 0.7x。

**但判断层把它们判成了「资料不够」。**

样本：

```
我大二了还想转专业来得及吗      相似度 0.762  → 判不能
转专业要多少绩点啊              相似度 0.762  → 判不能
本硕连读是不是直接读研          相似度 0.704  → 判不能
微专业能拿学位证吗              相似度 0.696  → 判不能
发表核心期刊论文能补绩点吗      相似度 0.687  → 判不能
公选课算进推免成绩吗            相似度 0.603  → 判不能
```

**瓶颈从检索转移到了判断层。**

## 六、为什么判断层会变严

推测（未验证）：多查询合并后，塞给判断层的是 **10 条来自不同查询的资料**。
资料变多、变杂，模型更容易得出「这些材料凑不出一个直接答案」。

判断层的 prompt 是 v7 定的第三版：「有能实质帮到用户的就行，拿不准倾向能」。
但它面对的是**更多但更杂**的输入——这和它被调优时的输入分布不一样了。

**这是一个典型的「改了上游，下游行为跟着变」**，而下游从来没在多查询的输入上被评测过。

## 七、下一步

| 优先级 | 做什么 | 理由 |
|---|---|---|
| 1 | 调判断层：给多查询的输入重新标定 | 现在它在吃检索的改善 |
| 2 | 判断层只看前 5 条（而不是 10 条） | 减少「资料多但杂」的干扰 |
| 3 | 把「相似度」也喂给判断层做参考 | 现在判断层只看内容，不看分数 |
